1 项目概述

1.1 背景与目标

项目配备两台 EWD611-868NW33（485 版）数传图传模块与一台网络摄像头，构成"远端采集—无线图传/数传—本地坐席"的链路：远端节点由摄像头接数传图传模块（模块 485 口再挂待控制设备），本地节点通过网口（RTSP 视频流）和 485 转 USB（AT 指令与透传数据）连接操作笔记本。本报告描述为该链路开发的 Windows 上位机控制软件的设计与实现。

软件目标按优先级归纳为四项：显示摄像头图像；通过 485 通道透传控制指令；配置图传模块关键参数并显示对端发来的数据；显示信道关键参数（RSSI、EVM、组网状态等）。工程目标为模块化、层次化、解耦合，Python 实现，独立 conda 环境，配套依赖清单、设计报告与部署手册。

2 需求分析与设计原则

2.1 功能需求

界面为单窗口多页签结构，共六个功能页：视频、透传控制台、数据、电台配置、信道监控、日志。命令行提供 selfcheck（无硬件全链路自检）、config（查看/生成配置）、templates（指令模板校验）、ports（串口探测）、gui（启动界面）五个子命令。

2.3 设计原则

（1）分层单向依赖：ui → services → protocol → transport → core，禁止反向引用；（2）消息驱动：跨层数据只经事件总线以带主题的消息流动，主题语义分为合并型（COALESCED，只关心最新值）与流型（STREAM，逐条不可丢）；（3）线程边界收口：后台线程的数据只经 UiBridge QTimer 节拍进入 Qt 主线程；（4）配置单一真源：任何覆盖（命令行 --set、程序内 overrides）汇入同一条 load_config → apply_overrides → _coerce 路径；（5）一切可 mock：不插硬件也能完整走通全部链路。

3.3 事件总线与数据流

主题负载类型投递语义主要消费方

主题划分遵循两个判据：值只关心最新的（遥测快照、参数视图）用合并语义，避免 UI 被旧值刷屏；每条都必须留痕的（AT 事务、告警、日志）用流语义，整批交付不丢条。这一区别由 UiBridge 的投递策略保证，页面侧无需感知。

3.4 线程模型

共四类线程：（1）Qt 主线程，仅 UiBridge 的 QTimer 把总线数据投递给页面；（2）LinkMonitor 轮询线程，按 link.poll_interval_s（默认 3s）驱动 AT 读序列并发布快照；（3）串口/UDP 收发线程，负责按空闲间隔切帧；（4）RTSP 解码线程，出帧经帧率上限（默认 25fps）与迟到丢帧后送视频页。服务层与协议层完全不知道 Qt 的存在，全部跨线程交互收口在总线与桥两处，保证 offscreen 测试可以脱离界面直接驱动总线。

3.5 关键设计决策

决策理由代价与对策
事件总线而非回调直连页面/服务/落盘解耦，新增订阅零改动调试链路变长 → 主题常量集中在 events.py，日志页可观察全部流量
参数注册表单一真源28 条参数的表单、校验、编解码、写计划同源生成，避免不一致注册表本身需要维护 → 每条规格附默认值与来源手册章节
AT 通道串口/UDP 可切换现场 485 转 USB 可能占用，UDP 走本地模块网口可并行两条通道行为差异 → 统一抽象到 transport 层接口下
freq 类参数存原单位、编码时按 scale 换算模块频点以 MHz×10 表达，界面直接显示 MHz换算点遗漏风险 → 编解码只允许走 registry 的 encode/decode
run.py 免打包入口而非 entry_points现场部署是"拷目录 + 建环境"，免重装不能 pip install 后全局命令 → 交付脚本 start_gui.bat 兜底

4 子系统详细设计

4.1 配置系统

配置为八段 YAML：app / video / serial / at / udp_at / link / passthrough / record / ui。装载链路为 load_config(path, **overrides)：先由 AppConfig.load 读取并填入 dataclass 默认值，再对 overrides 逐条按点号路径写入，写入时由 _coerce 依据目标字段当前类型做强制转换（bool 走 parse_bool，接受 true/1/yes 等文本），未知字段与无效路径不报错、只追加到 cfg.meta.warnings 供 config 子命令打印。这一条链路同时服务于配置文件、命令行 --set 与程序内覆盖，是"配置单一真源"原则的实现。

4.2 传输层

串口传输以 115200-8-N-1 为准（模块 RS485 固定波特率），支持 auto_detect 按常见 485 转 USB 芯片 VID（1A86/10C4/2341）优先猜测端口，空闲间隔（默认 30ms）作为分帧边界，独占失败时可选回退。UDP AT 通道支持端口探测与广播扫描。RTSP 传输封装 PyAV 拉流，5 秒打开超时、双解码线程；取流传输 video.transport 可在 TCP/UDP 间切换（默认 tcp），UDP 分支自动把 socket buffer_size 提到 4 MB 防内核缓冲不足丢包，切换入口与"三处命中"实现见 5.7。mock 传输与前三种实现同一接口，供无硬件自检与演示使用。

4.3 协议层与 AT 事务

参数注册表把 28 条参数分为普通可读写组、"信道遥测（只读）"组与"动作指令（只写）"组；每条规格含名称、读写属性、取值范围或选项、缩放系数与默认值。RadioService 的 read/write/plan/apply 全部返回结构化 dict，失败信息在返回值内，不向 UI 抛异常。

失败必留痕：AtClient 在真正上线指令前有"通道未绑定传输层""通道未打开""发送失败"三道前置校验，早期版本这三条路径直接抛异常而不发布 AtExchange，导致实机接线时出现"点读取全部没反应、日志页一条记录也没有"的排查盲区——现象与"根本没点"完全一致。现统一收敛到 _fail_unsent()：先向总线发布一条 ok=False 的 AtExchange（携带 line、channel、error 原因），再抛 AtError，使任何一次尝试都在日志页留下红色失败行，界面据第一条原因给出针对性引导。读取异步化：电台配置页"读取全部"会串行读十个以上参数，单参数超时 1.5s×重试，若在 UI 线程同步跑会冻结整窗分钟级、事件投递停摆。现由 _ReadWorker(QThread) 后台执行，按钮置灰显示"读取中…"，done 信号回填表格、finished 恢复按钮，页面关闭时等待线程收敛（超时则摘除父子关系保命，防"线程仍运行时被析构"崩溃）。批量短路：read_many 一旦命中通道级失败（未打开/未绑定），即把其余参数标记为"通道不可用，已跳过其余读取"，不再逐个空等超时，既快又避免误导为"模块全都不应答"。

4.4 服务层与链路轮询

会话装配入口为 build_session(path, *, mock, endpoint, video, record, telemetry, motion, **overrides)：装传输 → 装 AtClient → 装七个服务（其中遥测服务可由 telemetry.enabled 关闭、运动服务可由 motion.enabled 关闭或装配开关旁路）→ 返回 Session；mock=None 时遵循配置文件 app.mock。RadioService 刻意不发布 radio/params 主题，参数的发布点唯一收口在 LinkMonitor 轮询里，避免双写来源。

4.5 机器人遥测采集与状态栏

机器人侧经 485 送来的状态、电压、电流、电量、速度、位置由透传接收流旁路解析：services/TelemetryService 订阅 pt_bytes 主题且只消费 rx 方向字节块；解析器按 telemetry.frame.protocol 三选一：wheeltec（默认，机器人底盘实际协议）、binary（AA 55 头 20 字节占位帧）或 ascii（TLM,... 校验行）。Wheeltec 上行反馈帧为 24 字节定长：帧头 0x7B + 使能/急停标志 1 字节 + 10 个 16 位字段（前向/横向/角速度 ÷1000、三轴加速度 ÷1672、三轴角速度 ÷3753、电压 ÷1000）+ BCC 校验 + 帧尾 0x7D，校验不过则跳一字节重找帧头，避免半截帧串位；状态栏取其中的电压与平面速度（vx、vy 合成），电流/电量/GPS 该协议不上报即显示 --。匹配不到帧特征的字节原样放过，数据页与 Hex/ASCII 流水照常显示，解析失败只计数不吞数据。

一个入口三节拍：feed（串口回调线程）解析入缓冲，并按 display_throttle_hz（默认 2Hz）节流发布合并主题 robot/telemetry；1 秒新鲜度节拍在超过 stale_after_s（默认 3s）无有效帧时判定中断，"刚变过期"只告警一次并强制推一次事件让界面立即置灰；1 秒 CSV 节拍把积压样本冲刷到 data/telemetry_日期.csv；10Hz mock 节拍按当前协议组假帧走同一解析路径，实现无硬件演示。边沿告警（电池低压、急停、遥测中断/恢复）一律遵循"跳变才发"防刷屏规则，且恢复与置灰同样强制发布，界面灰/复即时切换。历史缓冲全量保留不受节流影响——数据完整性与显示频率解耦，累计里程按梯形积分（相邻速度均值 × Δt，Δt>5s 视为断档不补）在服务层结算。

界面侧 ui/widgets/TelemetryBar 挂视频页底部：状态/电压/电流/电量/速度/位置/定位 7 个数字格，缺数据统一显示 --，遥测中断整体灰字、电池低压与急停红色加粗并附悬停原因；下方双序列迷你曲线（电压与速度各自归一化）看趋势，"导出 CSV"仅发信号，由页面向服务取数、弹保存框完成复制。累计里程不再占用速度槽位、也不设切换按钮——它只在速度格的鼠标悬停提示、明细表格与导出 CSV 中给出，避免误触影响读数。控件唯一数据入口是 refresh(payload)，不持有服务引用，保持控件→页面→服务的单向依赖；进页时用服务历史回填曲线。

联调后机器人侧确认使用 Wheeltec 底盘协议，已实现为默认解析器（上行 24 字节反馈帧 + 下行 11 字节速度帧，见 4.6）。以下为规划期定义的两种占位帧格式（保留作备选，切 telemetry.frame.protocol 即可启用，界面零改动）：二进制 AA 55 | 长度 | 状态 1B | 电压 2B(0.01V) | 电流 2B(0.01A) | 电量 1B | 速度 2B(0.001m/s) | 经纬度各 4B | XOR 校验；ASCII 行 TLM,2,24.61,3.21,78,0.45,116.397428,39.909236*7F。数字区采用等宽数字字体避免数值跳动抖排版；窄屏时曲线区自动隐藏仅留数字。

4.5.2 端到端链路与方案原则

方案三原则全部贯穿到实施：（1）可插拔解析器——telemetry.frame.protocol 选择帧格式，新增格式只需加一个解析器类并在配置切换；（2）旁路截取——服务只订阅透传接收流的 rx 方向，与数据页显示、录制完全解耦；（3）mock 先行——10Hz 模拟源按当前协议组假帧、走同一解析路径，无机器人也能演示与验收界面。

4.6 机器人运动控制

批复需求为"视频页增加四个方向按键、松开即速度归零、最大速度放配置文件、要有加减速过程"。方案将其建模为 vx（前后，m/s）/ vr（转向，rad/s，左转为正）双通道速度指令：上/下键改 vx，左/右键改 vr。按住时目标速度取配置限幅的正负满值（max_linear_speed 默认 1.0 m/s、max_angular_speed 默认 0.5 rad/s），松开即目标归 0；实际速度对目标做斜坡趋近——加速用 accel 斜率（线速度 0.5、角速度 0.3），松开用 decel 斜率（线速度 0.8、角速度 0.5，减速快于加速更安全），到位吸附消除尾差。斜坡与限幅全部收在 advance(dt) 纯计算里，不碰 IO，无硬件可完整单测。

发送语义由服务内置的 ticker（节拍下限 50 ms）负责：速度非零期间按 send_period_ms（默认 100 ms）周期重发运动帧——按住时若某帧丢失，下一帧 100 ms 内必到，天然抗丢包；速度由非零回到 0 时恰好补发一次零速停止帧，此后空闲零发。组帧为双路：默认 motion.frame_protocol=wheeltec，按官方底盘下行速度帧组 11 字节帧——0x7B 帧头、2 字节预留、前向/横向速度（mm/s）与角速度（mrad/s）各填有符号 16 位大端（÷1000 还原），BCC 校验和与 0x7D 帧尾收口；逆时针（左转）为正，底盘反装时置 motion.invert_angular=true 翻转角速度符号；切 template 则回退 motion.frame_hex 模板组帧（占位符填速度×100 的有符号 16 位大端 hex）。帧经 PassthroughService.send(frame, kind="motion") 走 485 透传通道，与 AT 配置事务互不干扰；数据页"备注"列同步把下行速度帧译成语义句（如"速度指令：前向速度 0.500 m/s，角速度 0.100 rad/s"），上行反馈帧同列译"底盘反馈"文案。每次斜坡后服务把速度快照发布到合并主题 robot/motion，界面只读回显、不自行记账。

界面侧 ui/widgets/MotionPad 以十字五格排布四个方向按钮与中心状态行，按钮设 Qt.NoFocus 避免抢页面焦点；视频页 keyPressEvent 与 keyReleaseEvent 把 ↑↓←→ 映射到同四个方向，并对称过滤 isAutoRepeat：长按时系统会夹带重复的"按下/释放"事件对，两侧都只认非自动重复的那一次——按下只认首次、释放只认真正松手。早先只过滤了按下却漏掉释放，导致按住时中间的自动重复"释放"被当成松手、目标清零而速度"递增又回零"，现已修正；松开键与松开按钮语义一致。安全网四层：① 页面失焦或切离视频页触发急停（速度即时清零并补发停止帧，stop_on_focus_loss 默认开）；② "空发"守卫——并无运动时失焦不发帧，总线不多余；③ 会话 stop() 趁通道未关补发一次停止帧；④ 透传发送失败只在首次"跳变"时告警一次，节拍继续静默重试不刷屏。运动服务未装配或 motion.enabled=false 时，页面降级为方向盘停用并标注原因，视频其余功能不受影响。

4.7 界面层

主窗口从 pages 注册表按序创建六个页面，注册表以 key + 标题 + 说明 + 工厂函数声明页面，新增页面零改动主窗口。BasePage 定义统一契约：on_batch(topic, items) 接收桥的批量投递、on_slot 接收节拍回调、say 走状态栏、on_close 释放订约。六页要点：视频页帧到即绘、支持录制与抓图，底部常驻遥测状态栏（见 4.5），下区十字方向盘支持按钮与键盘四向运动控制（见 4.6）；控制台页 Hex/ASCII 互转、模板下发、CRC16 自动追加；数据页以九列表格展示对端透传数据流与参数视图，列宽可自由拖动、备注列对 Wheeltec 上下行帧做语义解读；电台配置页由注册表生成表单，支持读取/编辑/预览/下发四操作；信道监控页双轴 RSSI/EVM 历史曲线（按快照时间戳去重，1200 点环形上限）加链路指标卡加 STA 九列表；日志页三源合屏、来源与级别双维过滤、HTML 转义着色、4000 块硬截断、录制路径一键查看。

4.8 落盘与记录

RecordService 订阅总线并落盘：data/logs/at_*.log（AT 流水）、data/logs/events_*.log（事件）、data/passthrough/bytes_*.log（透传字节）、data/passthrough/link_*.csv（链路遥测表）、data/recordings/（录像）与 data/snapshots/（抓图）。paths() 汇总当前句柄供日志页展示，文件名以启动时间戳区分场次。机器人遥测表 data/telemetry_日期.csv 例外，由 TelemetryService 自带节拍冲刷（见 4.5），导出入口在视频页状态栏。

5 关键技术与难点

5.1 RTSP 低延迟解码

默认使用摄像头子码流（704×576）以带宽优先；取流传输 video.transport 可选 TCP/UDP（见 5.7）。延迟控制分两级：收流侧 FFmpeg max_delay = buffer_ms×1000（代码默认 300 ms，现场建议 100 ms 起步）压缩协议层缓冲；放帧侧队列容量 pacing_frames（默认 5，现场 3）内按 max_dwell_ms 时间预算（默认 120 ms）做时间基跳帧——放帧停留超预算即丢弃积压、只放最新帧，队列溢出另计丢帧（frames_dropped 为溢出、frames_skipped 为跳帧，两本账分开）。OSD 右下角显示"显示N帧 · 停留Xms [跳帧M]"：若停留持续贴近预算上限且跳帧猛涨，说明解码跟不上流速率，应回调小 buffer_ms 或改走 UDP 取流。渲染侧按 render_fps_limit=25 限帧，保比例缩放与 OSD 叠加可选。

5.2 RSSI/EVM 曲线与阈值告警链

难点在合并型主题与历史曲线的配合：同一快照可能被多次投递，曲线在入点处按时间戳单调去重，保证"3 次重复投递只画 1 个点"；进页面时先用 radio 服务的历史缓存回填曲线，再增量接续；告警链从轮询判阈值发 AlarmEvent 起，经总线同时到状态灯与日志页，避免多处重复判断。

5.3 全链路 mock

仿真电台实现了 AT 命令语义应答（参数读写、组网状态）、RSSI 在 [-98,-52] 区间的 1 秒随机游走（因此会周期触发 -85/-92 告警，属预期演示效果）、STA 列表与丢包模拟；仿真视频源生成测试图样。自检与 CI 完全基于 mock 链路运行。

5.4 无硬件降级

所有页面在对应服务缺失或未连时仍可打开：按钮禁用并给原因提示、指标显示占位破折号、状态显示"未知"灰字。串口缺失时 AT 通道打开失败仅记 ERROR 日志不阻断界面启动。

5.5 机器人遥测：Wheeltec 协议接入与旁路容错

遥测解析器三选一：默认 telemetry.frame.protocol=wheeltec，按官方 24 字节上行反馈帧解析（0x7B 头 0x7D 尾、10 个 16 位大端字段按各自标度还原、BCC 校验，失配时跳一字节滑动重同步）；规划期的 binary 与 ascii 占位解析器保留作备选，换协议只需新增一个解析器并切配置，解析与展示链路不动。服务以"旁路"方式订阅透传原始流：匹配不到帧特征的字节原样放行，数据页透传功能零回归。显示节流（默认 2Hz）与 CSV 落盘（全量 1 秒节拍冲刷）刻意解耦——界面刷新频率低不影响留痕完整性；置灰与恢复两个边沿均绕过节流强制发布一次，保证状态切换即时可见。

5.6 运动控制：斜坡纯计算与"恰好一次"的安全收口

运动控制的难点全在异步事件下的安全边界，三个关键取舍：（1）斜坡写成纯函数 advance(dt)，限幅、到位吸附与补发判据都不触 IO，22 条服务层用例可在无硬件下把加速、滑行、斜向组合、周期重发的帧序列逐一断言；（2）停止帧在三个边沿各"恰好一次"——速度回零边沿、急停、会话退出前趁通道未关补发，空闲态由守卫拦住零帧外发，机器人不会收到悬空序列，也不会被无意义停止帧刷屏；（3）界面与服务共用单一状态源（服务快照经 robot/motion 回显），方向盘不自行记账，读数与实发速度天然一致，长按自动重复（isAutoRepeat）在 press 与 release 两侧对称过滤——按下只认首次、释放只认真正松手，杜绝"按住时速度递增又回零"与"松开丢事件导致持续运动"。测试还实证了两个 Qt 细节：便捷构造器 QKeyEvent(type, key, modifiers, text, autorep, count) 第 5 位是 autorep 而非重复计数，以及 QPushButton 无公开 press()——按钮链路测试直调信号槽等价且更稳。

5.7 RTSP 取流传输：TCP/UDP 运行时切换

TCP 取流稳定不花屏但重传缓冲抬高端到端延迟，UDP 延迟低但丢包可能花屏，故把 video.transport 做成可运行时切换的配置项：视频页工具条"传输"下拉即选即效并自动写回 config/app.yaml。实现要点四条：（1）配置层 _validate 对取值规范化，非法值一律回退默认 tcp；（2）一次切换"三处命中"——更新内存配置、取流中则以新传输重启拉流线程、持久化写回 yaml（写盘失败仅告警不影响内存生效，可传 persist=False 只切内存）；（3）UDP 分支自动把 PyAV socket buffer_size 提到 4 MB，防内核接收缓冲不足丢包；（4）出现花屏切回 TCP 即恢复，行为与配置始终一致。该开关使"低延迟试验"无需改文件重启进程。
